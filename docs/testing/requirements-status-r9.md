# FF-1 requirements delta - round 9

Assessment date: 2026-11-05. This document updates the frozen [R8 requirement-by-requirement matrix](requirements-status-r8.md), using the same [original user specification](../product/original-user-specification.md). Rows not listed here retain their R8 status. The R7 and R8 source archives and retained evidence are historical snapshots; current code or a later test does not change their results.

States retain the R8 meanings: **S** implemented and exercised within the stated software/synthetic scope; **P** partial or a narrower substitute; **N** feasible missing software/integration; **V** vendor, supply, implementation-data or publication-rights dependency; **H** physical implementation/measurement not performed. No result here establishes a manufactured FF-1, physical calibrated camera or production updater.

## Integrity and recovery review

The independent review found concrete faults, rather than treating the new binding's checksum as sufficient proof of the enclosing record:

| Observed fault | Disposition and verification |
| --- | --- |
| Reference startup accepted a valid bound snapshot inside a capture record with a different request UUID, zero completed actual exposure or inconsistent SQL/JSON status, and reported a healthy journal. | Reproduced with one real disposable bound capture followed by one journal-field change per case; original journals were not edited. Reference correction and its final tests are owned by the service implementation and must be recorded in the final R9 evidence. |
| State could contain a calibration summary with another sensor, mismatched IDs or true hardware/correction claims. | Fixed in shared pure validation used by native and HTTP state readback. Legacy omission is allowed; present invalid summaries fail. |
| A valid outer v2 snapshot could contain native evidence referring to a different calibration/frame or exposure/gain. | Fixed: optional evidence must describe the same request/frame, sensor, calibration and settings. Legacy worker evidence may legitimately omit `capture_id`; when present it must match the request and outer capture. An `unknown` record may deliberately withhold outer frame/actual outcome fields while retaining valid worker evidence: the nested frame must still match the request UUID and synthetic actual values must match the immutable request or known outer values. Validation never fills withheld fields or promotes unknown to complete. Other partial evidence, numeric Boolean impostors and unsupported physical/correction flags fail. Python v2 records need not invent native evidence. State's `last_capture` uses the same checks. |
| HTTP500 with a `not_found` JSON code was returned as a missing original capture. | Fixed: only actual HTTP404 plus `not_found` yields `None`. The regression uses a real bounded loopback server. No error response causes capture replay. |

The client fixes add no file inspection, device mutation or repair. A binding checksum establishes content identity and accidental-corruption detection, not authorization or authenticity. The existing same-user filesystem race boundary is not promoted to atomic sandboxing.

## Unchanged gates and feasible next work

The exact R8 physical/vendor gates remain open: written supply/electrical/register/RAW14/publication rights; an authorized sensor board and first light; open receiver/initialization, FPGA lanes/protocol/CDC/DMA and real V4L2/libcamera adapter; selected body/SoM/MCU/display/power interfaces; real package/filter/image-plane/mount geometry and two-mount optical tests; measured color/black/defect/shading/temperature calibration; battery/thermal measurements; real media slow/full and power-cut tests, 1000 actual RAW/8-hour endurance, and an independent manufactured/rebuilt camera. Generic QEMU and software-generated DNGs satisfy none of those physical measurements.

Still-feasible software work is not all vendor-blocked: proper DaOS integration after source/rights resolution, measured-calibration data schemas and synthetic algorithm/binding tests, stage-aware progress/deadlines and recovery budgets, supervisor-event integration, production look/preview processing, removable-media lifecycle, actual signed update/bootloader integration and source-bound automated target CI. The present read-only system plus writable data disk is not four separately provisioned OS/photo/configuration/calibration partitions. The virtual A/B model is a useful narrower implementation, not production update completion.
