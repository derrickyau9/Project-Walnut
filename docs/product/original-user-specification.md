HassleFree FF-1

从 DaOS 到开源全画幅相机：0→1 工程方案

The camera built by the people, for the people.
Open Hardware. Open Firmware. Open Photography.

项目主线：从你的 DaOS 中提取通用框架，建立独立的 DaOS Camera；在其下新增原生成像服务、FPGA 采集链路和模块化硬件，最终交付一台社区可以自行制造、编译、维修和扩展的全画幅相机。

第一代不是“换皮哈苏”，也不是把企业后台界面塞进机身。它应当是一台以摄影为基本功能、以开放接口和可编程工作流为差异化的相机。

本文中的新服务名、接口、性能指标及目录均为拟议设计，不是声称它们已经在你的仓库中实现。

一、从你现有的 DaOS 出发，而不是重新发明一套框架

1.1 已核实的代码基础

我查看了你的 daos-capability-runtime 的 README、依赖配置、来源说明，以及 schema.ts、control.ts 和 engine.ts 的相关实现；同时查看了 DaOS-Hospitality、DaOS-iHOMI 的项目说明。

最适合直接作为相机项目起点的是：

derrickyau9/daos-capability-runtime

它已经有 React、TypeScript、Vite 的界面基础，以及基于 Node.js 的执行服务。项目的核心模式是：发现操作流程，将其保存为带输入、输出和检查点的能力描述，再进行不依赖模型调用的确定性重放。

但它目前仍然是网页操作运行时：动作类型主要是 click / fill / read，Schema 包含具体业务字段，执行器直接依赖 WebSurface。因此，不能仅增加一个“Camera”页面就把它当成相机系统。

正确的复用方式如下。

现有基础	相机项目中的用途	需要做的改变
DaOS App Shell、导航、通知、状态组件	桌面开发控制台、远程相机控制台	去掉业务页面，增加拍摄、设备、标定和诊断视图
Capability Schema	可分享、可重放的拍摄配方	从网页动作改为原生相机能力调用
检查点与预期状态验证	确认曝光设置生效、帧接收完成、文件真正落盘	从 DOM 标记改成设备状态与事件
控制权与 epoch 机制	仲裁机身操作、远程控制和自动化任务	移到相机原生服务中，不能只保存在 Node 进程里
执行证据与日志	拍摄请求、实际参数、帧号、错误及标定版本追踪	增加图像采集专用元数据
模型连接层	可选的拍摄配方生成助手	不进入快门、读出、写盘等实时链路

现有 DaOS 的来源说明已经明确列出可复用的界面、主题、工作流、日志和指标组件；这部分是实际存在的积累，不需要从零重做。

1.2 不把两个业务系统整体搬进相机

DaOS-Hospitality 是包含入住、门锁、员工、会员及业务服务的私有平台；DaOS-iHOMI 包含零售、订单、库存与企业专用实现。它们可以提供经过验证的设计经验，但不应该成为相机固件的运行依赖。

建议形成这样的关系：

DaOS 通用组件与设计积累
        │
        ├── DaOS Hospitality
        ├── DaOS Retail
        │
        └── DaOS Camera
                ├── 相机控制台
                ├── 拍摄工作流
                ├── 设备与插件管理
                └── 诊断、标定、更新
                         │
                  HassleFree 原生成像系统
                         │
                  HassleFree FF-1 硬件

DaOS Camera 是新的领域实现；Linux 内核、板级支持和高速图像采集是它下面的新工程层。

4.2 主控路线：先采用 ARM＋FPGA 一体平台

第一条原型路线建议采用 Zynq UltraScale+ MPSoC 类平台，而不是一开始同时调试独立 FPGA、RK3588、PCIe 桥和第二套内存。

拟议分工：

部分	工作
FPGA 可编程逻辑	传感器数据接收、组帧、DMA、统计及部分预览处理
ARM Linux	相机服务、存储、界面、DaOS 工作流
实时处理单元或专用逻辑	精确触发、事件时间戳和需要确定时序的控制
外置小型 MCU	独立电源管理与系统监督

实验室参考平台可选 ZCU102 这一类带足够高速收发器的开发板。 AMD 的资料显示，它的两个 FMC HPC 接口分别连接了八路 GTH，适合作为八通道接收原型的硬件起点；但传感器接板、电平、参考时钟和接收逻辑仍需自行匹配。

最终机身再换成小型 SoM＋自研载板。不要第一版就同时承担大规模 BGA、DDR 布线和整机小型化。

五、传感器与采集硬件：先解决第一张真实 RAW

5.1 IMX410 是候选，不是已经落实的供应链

Sony 的公开资料确认 IMX410 是全画幅背照式传感器，支持八路 SLVS-EC、14-bit 转换；公开模式表列出 6064 × 4040 有效成像输出，以及该模式下最高约 19.2fps 的 14-bit 读出。它还有其他位深和读出模式。

这与项目定位匹配，但必须分开以下三件事：

产品在目录中存在、能够买到样品、能够公开完成驱动所必需的实现，是三个不同条件。

FRAMOS 的产品页面目前将该器件采购指向 RESTAR FRAMOS；这提供了询价入口，并不等于已经获得单片价格、库存或开放驱动许可。

供应商询价必须一次问完整

类别	必须得到的答案
供应	样品价格、最小采购量、交期、后续供货安排
电气	完整引脚、供电时序、时钟、布局参考
控制	初始化序列、寄存器、曝光与增益生效规则
数据	SLVS-EC 版本、速率、通道配置、RAW14 数据打包
成像	CFA、有效区、光学黑区、坏点及必要校准要求
光学机械	封装、感光面基准、盖板玻璃及滤镜条件

5.2 SLVS-EC 接收器是独立工作包

不能把“有免费的 FPGA IP”写成“已解决开源采集”。

例如，Microchip 的 SLVS-EC 接收器提供免费的加密 RTL，其公开支持列表包含 RAW8、10、12、16；这既不等于源代码开放，也不能直接据此认定 IMX410 的 RAW14 模式已得到支持。

建议分两条路径：

Bring-up 路径：在条件允许时使用厂商参考接收器，尽早确认传感器、电源、时钟及 PCB 是否正常。

开放交付路径：获得可公开的接收实现，或依据允许使用的规格独立实现必要子集，并提供测试向量和验证环境。

两条路径共用相同的像素流输出接口，避免以后替换接收器时重写整台相机。

最终公开版本的“完整可复现”验收，必须包含接收逻辑及传感器初始化这一段。仅发布它后面的 UI 和应用不算完成。

5.3 FPGA 数据流水线

拟议最小实现：

高速接收器
    ↓
通道恢复、对齐与协议解析
    ↓
数据包 / 行 / 帧完整性检查
    ↓
Bayer 像素解包
    ↓
frame_id + 时间戳 + 实际曝光元数据
    ↓
异步 FIFO / DMA
    ↓
Linux 可管理的帧缓冲区

第一阶段只保证正确收数据，不把复杂降噪、AI、JPEG 和高级色彩处理塞进 FPGA。

需要从一开始提供错误计数：失锁、包错误、行长异常、帧长异常、FIFO 溢出及 DMA 超时。错误帧必须有明确状态，不能悄悄当作正常照片保存。

5.4 传感器板设计

传感器板应是独立、可维修的模块，包含传感器、电源、时钟、温度监控、身份信息及高速连接接口。

具体设计要求是：

* 电源轨、启动顺序和复位时序由器件资料决定，不猜测。
* 高速链路按实际速率和阻抗设计，保持连续参考平面及可控回流路径。
* 模拟电源与大电流开关噪声通过布局、供电和滤波管理，不靠随意割裂地平面。
* 预留电源、时钟、复位和控制总线测试点。
* 传感器承载结构与镜头承力结构分开，不能让镜头重量弯曲传感器 PCB。

传感器模块的“可更换”是维修和升级能力，不是热插拔能力；更换后要重新校准。

六、带宽与缓存：先算清楚，再承诺帧率

按 6064 × 4040 计算，以下为纯像素数据量，未计额外行、元数据及文件开销。

项目	计算结果
像素数	24,498,560
紧密打包 RAW14	约 42.87 MB/帧
展开到 16-bit 容器	约 49.00 MB/帧
1fps、16-bit 容器	约 49 MB/s
5fps、16-bit 容器	约 245 MB/s
19.2fps、16-bit 容器	约 941 MB/s
8 帧缓存	约 392 MB
16 帧缓存	约 784 MB

这是基于 Sony 公开成像尺寸的算术计算，不代表整机已能达到这些吞吐量。

因此，首台原型的设计目标可以是：

4GB 系统内存、明确预留的 DMA 缓冲区域、至少八帧 RAW 缓存，以及经过实测的存储写入能力。

还必须区分两个容易混淆的点。

拍一张每秒，不代表接口只需要处理每秒一张的平均带宽

传感器可能在短时间内高速输出一整帧。FPGA、FIFO 和 DMA 必须承受该模式的瞬时数据速率。

分开预览和保存，不代表可以保证无黑屏

预览队列可以丢弃旧帧，始终显示最新画面；照片队列不能无声丢弃已接受的拍摄。

但若传感器从预览模式切到高位深静态模式，仍可能出现停顿。FF-1 应显示真实状态，不能用重复旧画面冒充持续实时取景。

首发先做到“慢存储不拖死操作界面”，再优化连续取景。

七、DaOS Camera：具体怎样改造现有代码

7.1 提取，而不是整仓复制

建议新建独立项目，将可复用代码按文件来源导入，并记录来源版本。

现有 DaOS-iHOMI 明确说明没有统一覆盖整个仓库的开源许可证；DaOS-Hospitality 标注为专有软件；公开 Runtime 的来源文件也说明上游框架导出时没有许可证文件。因此，不能把整个现有仓库直接继承为一个已获完整开源授权的相机项目。

相机项目的做法是：为明确属于你、准备开放的通用组件单独授予许可证；业务专用代码不进入新项目。

将现有网页动作升级为领域能力：

“要求设置成 1/100 秒”和“这一帧实际使用了 1/100 秒”必须是两个不同字段。

7.3 camerad 是唯一控制权威

机身 UI、远程控制和自动化工作流都不能自行直接改传感器寄存器。

它们统一向 camerad 提交请求，由它负责状态验证、资源仲裁、参数应用及执行确认。

建议采用 C++ 原生服务，与 libcamera、V4L2 和 Qt 的接口保持直接。TypeScript 保留在 DaOS 控制台和工作流层，不承担高频像素处理。

libcamera 本身已经区分 Pipeline Handler 与图像处理算法模块，并通过 Media Controller/V4L2 管理底层管线；自研硬件仍需实现对应驱动和适配，不能认为安装 libcamera 就自动支持 IMX410。

7.4 现有控制权机制需要升级

你的 Control 已经有 epoch、token 和串行 gate，这个设计思想值得保留。但它是单进程 Promise 队列；从实现看，某个 gate 内的操作长期不返回时，后续控制操作也可能排在后面等待。

相机版必须增加：

服务端控制权、明确超时、可取消任务、独立进程监督，以及不依赖该队列的硬件恢复通道。

工作流暂停不能依赖一个已经挂死的插件主动配合。

7.5 不对拍摄进行盲目自动重试

“设置白平衡”和“拍摄一张照片”不是相同类型的操作。

设置参数通常可以重复；拍摄请求在通信中断时，可能已经触发但尚未收到完成通知。

因此采用：

持久化请求 ID → 执行 → 查询同一请求的状态 → 判断是否完成。

状态无法确认时明确返回 unknown，而不是自动再拍一张并声称实现了“恰好一次”。

这比把现有网页 replay 的重试方式直接搬过来更重要。

    └── 可选镜头电子控制板

首批实现 Sony E 和 Canon EF 两个机械模块，沿用前面确定的方向。

Sony 的公开资料列出 E 卡口法兰距为 18mm、EF 为 44mm；Nikon 官方资料则确认 Z 卡口采用 16mm 法兰距和 55mm 内径。这些尺寸会直接决定机身前部的结构包络。

8.2 不提前把通用基准面锁死在“12mm”

前面讨论过 12mm，但现在进入工程设计，不能把它直接作为定案。

最终基准位置必须同时容纳：

传感器封装与盖板、滤镜、卡爪后伸部分、电子触点、镜头后组、遮光结构及装配公差。

先做剖面与干涉模型，再冻结 HUMI 尺寸。

为 Nikon Z 留下设计可能性，不等于尚未验证就宣布支持 Nikon Z。

8.3 精度与维护方式

推荐采用金属承力结构、明确的定位基准、定位销及可更换垫片。塑料外壳负责外观和握持，不负责维持光学基准。

初始验证目标可设为：

项目	原型验证目标
轴向调整	支持微米级垫片调整
重复装配	多次拆装后重复测量法兰位置
平行度	中心与四角成像验证，必要时三点调整
承力	镜头负载不传给传感器 PCB
可维护性	每个模块有 ID、版本和校准记录

具体公差需要由加工能力、镜头测试及实际画面决定，不以未经验证的数字作为产品承诺。

8.4 机械兼容和电子兼容分开公布

第一代的实际测试镜头必须具备不依赖机身电子协议也能工作的对焦及光圈控制。

“可以安装 EF 卡口”不能被描述成“所有 EF 镜头都可正常调光圈与对焦”。

后续电子模块采用统一的机身侧控制接口，由模块 MCU 处理镜头侧电平和时序。兼容表按具体镜头型号及固件记录：

机械安装
光圈控制
镜头识别 / EXIF
对焦驱动
自动对焦
镜头防抖

这些是六项独立能力，不合并成一个模糊的“支持”。

⸻

九、成像、DNG 与色彩：建立自己的画质体系

9.1 原始数据、预览、风格输出三者分离

传感器原始 Bayer
    ├── 保留原始数值与必要元数据 → DNG
    │
    └── 黑电平 / 坏点 / 校正
            ↓
          去马赛克
            ↓
       白平衡与颜色转换
            ↓
       曝光映射 / 色调曲线
            ↓
      可选 LUT / 风格处理
            ↓
       屏幕预览 / JPEG

项目的色彩特点应来自自己的测量和调校，而不是把某家相机的色彩文件移植过来。

9.2 DNG 不是给 RAW 字节加一个后缀

DNG 有公开规范及可用于读写的 SDK，适合作为第一代相机的交换格式。

首版需要正确处理 CFA、有效区域、位深、黑电平、白电平、白平衡及颜色标定信息；这些字段本身就是 DNG 的处理模型的一部分。

项目验收应要求：

至少两套独立的软件能够正确解码；解码得到的 Bayer 数值与采集缓冲区一致；颜色和裁切不是“碰巧看起来正常”。

16-bit 容器存放 14-bit 数据可以作为实现方式，但不能因此把相机宣传成真正的 16-bit 采样。

9.3 标定从原型阶段开始

每台机器建立与传感器序列号绑定的标定包，至少覆盖：

标定内容	作用
黑电平随模式、增益及温度的变化	避免不同条件下出现错误基线
坏点与热像素	记录并可追溯地处理异常像素
响应与均匀性	识别固定图案与空间不均匀
颜色矩阵	建立自己的颜色转换
光学组件与镜头组合	记录暗角、偏色和适配差异
传感器平面	检验中心与边角合焦一致性

标定数据放在独立持久化区域，有版本、校验和及导出能力，不能在系统更新时覆盖掉。

RAW 默认不烘焙用户 LUT。拍摄风格与传感器校正使用不同的版本号，让用户知道哪些处理改变了预览，哪些处理改变了输出。

9.4 自动对焦按能力逐步增加

顺序应是：

手动对焦辅助 → 已支持镜头的电子驱动 → 单次对比度 AF → 连续 AF → 有条件的 PDAF。

PDAF 必须以传感器确实提供相应数据、映射和标定条件为前提，不将“以后加 AI”当作替代方案。

十、系统、界面与 DaOS 的真正差异化

10.1 软件栈

层	建议实现
启动	U-Boot＋恢复启动路径
系统	固定版本的 Linux BSP，原型阶段用 Buildroot 管理系统镜像
设备驱动	传感器控制、FPGA DMA、显示、输入、电源管理
相机框架	V4L2＋libcamera 适配
原生核心	C++ camerad、图像处理及 DNG 写入
机身界面	Qt/QML
开发与远程控制台	复用 DaOS React/TypeScript
工作流	从现有 Runtime 提取并改造的能力执行器
标定工具	Python 离线工具
系统更新	A/B 镜像＋启动健康确认

V4L2/videobuf2 和 DMA-BUF 提供了管理与共享视频缓冲区的基础，但需要实际验证内存布局、同步、CPU 访问及驱动支持；不能把“使用 DMA-BUF”直接等同于所有路径都零拷贝。

10.2 两套界面，共用一套相机 API

桌面开发控制台直接利用你的 DaOS：显示链路状态、曝光请求、温度、错误、帧率、工作流和标定数据。

机身界面重新做成适合拍摄的布局：大取景区域、清晰曝光信息、少层级菜单、实体拨轮优先。

React 组件不能直接变成 Qt 组件；复用的是设计语言、状态模型和接口，而不是宣称 UI 代码能无成本跨框架迁移。

10.3 第一代就做出“DaOS 相机”的特点

真正有辨识度的不是在相机里放一个聊天窗口，而是：

把拍摄过程变成可保存、可分享、可检查的执行配方。

首批配方可以包括包围曝光、间隔拍摄、产品摄影固定流程、暗场采集和标定任务。

例如，一个包围曝光配方的语义是：

取得控制权
→ 检查存储与传感器状态
→ 应用第一档曝光
→ 等待参数实际生效
→ 拍摄并确认文件落盘
→ 执行后续档位
→ 恢复原始设置
→ 释放控制权

LLM 可以把自然语言转成待确认的配方；执行已保存配方不需要联网或模型。

即使整个 DaOS 自动化服务停止，用户仍然可以通过基本机身界面拍照。

十一、电源、散热、挂死恢复与更新

11.1 独立 MCU 管什么

电源 MCU 管理启动、关机请求、按键、电池状态、关键电源开关和系统监督。Linux 可以请求动作，但 MCU 保留独立判断和复位路径。

精确曝光时序交给传感器、FPGA 或实时控制单元，不交给浏览器定时器。

11.2 先测功耗，再做外壳

分别测量待机、预览、单张保存、持续拍摄、文件传输和充电时的功耗与热点。

传感器、FPGA/SoC、存储和电源器件分别建立热路径。V1 不做 IBIS，可以先采用固定传感器承载和明确的导热结构。

续航只能用实测功耗计算。例如，假设电池 36Wh、可用比例 85%、平均负载 15W，则估算约为 2 小时；这是计算示例，不是 FF-1 已验证续航。

11.3 判断挂死看“进度”，不是只看进程活着

监控应该分层：

层级	观察的进度
FPGA	链路状态、行/帧计数、错误计数
DMA	完成序号、超时及缓冲归还
相机服务	请求阶段和 frame_id 推进
存储	写入进度、提交结果
UI	自身响应，不代替采集健康判断

长曝光期间没有新帧不等于挂死。期限必须结合：

当前阶段＋计划曝光时长＋模式读出时间＋允许的处理或写入时间。

恢复顺序应尽量局部化：

停止故障插件
→ 重建该工作流
→ 重启相机服务
→ 重新初始化采集链路
→ 必要时重启主系统

加入恢复次数预算，避免“恢复失败—重启—再次恢复失败”的无限循环。

11.4 存储与固件分别恢复

照片先写临时文件，再完成同步与最终提交；系统记录哪些拍摄已提交、哪些中断。具体掉电行为要在选定文件系统和存储卡上做测试，不能仅凭一次 fsync 就宣布任意掉电都无损。

系统更新采用 A/B 槽位，新版本通过启动和核心设备健康检查后才标记成功。RAUC 提供此类槽位管理和启动成功确认机制，但需要与启动加载器及项目自己的健康判断结合。

系统槽位、用户照片、配置和标定分区应彼此独立。

十二、从 0 到 1 的实施路线与验收

按验收关卡推进，而不是按“外壳完成了多少”判断进度。

阶段	主要工作	必须交付	通过条件
G0：项目拆分	提取 DaOS 通用组件，确定范围和来源	产品定义、来源清单、初版许可证、架构决策	新项目能脱离两个业务系统独立开发
G1：软件相机	实现 HF-Sim、相机 API 和最小控制台	合成 Bayer→DNG→回读的完整流程	像素一致性、取消、异常和重启测试通过
G2：器件可行性	核实传感器、资料、接收器及公开条件	选型记录、接口表、报价与供应记录	必要资料到手，核心实现具有可发布路径
G3：真实采集	传感器板、FPGA 接收、控制与 DMA	第一张真实全画幅 RAW	连续采集一批完整图像，无未解释的数据错误
G4：独立拍摄	Linux、显示、按键、存储	不连电脑的相机原型	本机取景、曝光、拍摄、回放和导出完整工作
G5：模块化机身	HUMI、两个卡口、精密结构	可重复装配的机械原型	两种卡口均经实际镜头验证合焦与边角表现
G6：画质与稳定性	标定、色彩、错误恢复、电源测试	标定包和测试报告	DNG 可重复解析，异常不会导致不可恢复状态
G7：独立复刻	完善制造和构建材料	完整发布包与组装文档	非项目作者能构建并完成拍摄

12.1 G1 不是“先画一个 UI”

HF-Sim 至少提供合成 Bayer 图、曝光变化、模式切换、帧延迟、损坏帧、存储不足和设备断开。

它验证的是相机软件契约，不是假装已经仿真了 IMX410 的全部电气行为。

这一步能让你立即开始 DaOS Camera，而不必等昂贵传感器到货。

12.2 G3 的 First Light 顺序

真实硬件调试按以下顺序执行：

电源与时钟 → 控制通信 → 接收器锁定 → 数据完整性 → 原始 Bayer → 正确曝光响应 → DNG → 预览。

不要在第一张 RAW 还不可靠时，用复杂 ISP 或 UI 掩盖数据问题。

12.3 V1 发布测试矩阵

建议把以下内容写成可重复执行的测试，而不是演示视频：

测试	初始验收目标
RAW 完整性	1,000 张连续采集样本逐张验证
长时间运行	8 小时运行，错误全部有记录和解释
模式切换	重复切换，无旧参数或旧帧误关联
慢卡与卡满	明确拒绝或排队，不把未保存显示为已保存
插件崩溃与挂死	基本拍摄路径保持可恢复
非正常断电	在不同写入和更新阶段进行重复测试
卡口重复安装	测量并记录法兰位置及画面变化
标定恢复	重刷系统后标定仍存在且能正确关联传感器
源码复刻	从干净环境构建，并由第二位开发者完成验证

这些数字是项目测试目标；随着原型结果再调整测试规模与门槛。

普通 CI运行 TypeScript、C++、接口兼容、DNG 回读和故障注入测试。

硬件在环测试放在真实开发板旁的自托管机器上，控制电源、拍摄、读取日志并验证输出。

这样社区贡献者不必先买全画幅传感器，仍然可以开发 UI、工作流、DNG、标定及测试工具。

十四、人员、预算与推进节奏

14.1 你的主导位置

你适合直接主导：

产品定义、DaOS 提取、相机 API、工作流、系统整合、开发工具、诊断与社区交付。

最值得补齐的是一位真正有高速接口与 FPGA 调试经验的合作者；机械光学和成像标定可以阶段性协作。

硬件工程师的关键价值不是画一块“看起来像主板”的 PCB，而是把传感器时序、接收链路、内存吞吐和电气问题实际闭环。

14.2 原型研发费用

以下是项目预算预留，不是供应商现价，也不是单台量产成本。尤其传感器费用必须以正式报价替换。

费用类别	预留 USD
软件验证与辅助器件	$300–1,200
传感器样品及相关评估资源	$2,000–8,000
FPGA 开发平台／SoM	$1,500–5,000
多轮 PCB、装配与返工	$2,000–6,500
机身、卡口与机械打样	$600–2,500

投入顺序应当是：

先完成软件闭环和资料核验，再采购高速采集平台；先得到可靠 RAW，再投入整机 CNC。

14.3 排期方式

对于你主导、另有一名硬件/FPGA 核心协作者并获得阶段性机械与标定支持的情形，可以先按 9–18 个月的研发规划窗口组织工作。这是资源规划假设，不是已验证工期；供应和资料交付应独立跟踪。

第一轮迭代只要求完成五件实物或代码交付：

交付	内容
项目范围	FF-1 PRD 与不纳入 V1 的功能清单
DaOS 提取	可独立运行的 Camera Console
相机接口	版本化 Schema、状态机和能力查询
软件闭环	HF-Sim 产生 Bayer，保存 DNG，再验证回读
器件调查	IMX410、接收器、公开实现及预算的核验表

做到这里，项目已经不再是一份概念书，而是一个能测试、能接受贡献、能继续接入真实硬件的工程项目。

最终定案

HassleFree FF-1 应当是“以 DaOS 为可编程控制层的开放相机”，而不是“运行 DaOS 网页的一块全画幅传感器板”。

它的三项核心资产分别是：

可信的成像链路——每一帧从传感器到 DNG 都有明确的参数、完整性和标定记录。

可更换的 HUMI 卡口——机械和电子能力分层，兼容性按实际测试公布。

DaOS 拍摄能力系统——拍摄流程可以保存、重放、检查、扩展，而且不依赖云服务。
